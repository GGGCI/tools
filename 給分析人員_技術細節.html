0. 名詞速查(先看這個)

SIEM
資安事件集中管理平台。把防火牆、WAF、IPS 等各種設備的 log 收進來一起看。你手上這批就是從 SIEM(ArcSight)匯出的。
ArcSight
一套 SIEM 產品(本案的平台)。它有「相關性規則(correlation rule)」功能,可以把多條事件組合判斷。
FW / 防火牆
管「誰能連到誰、哪個埠」的設備。本案是 PAN-OS(Palo Alto)。
WAF
網站應用防火牆,專門看 HTTP 網頁請求、擋網頁攻擊。本案是 Imperva SecureSphere——它幫我們記下了網址、瀏覽器身分等細節。
IPS
入侵防禦系統,比對「攻擊特徵(簽章)」。本案是 Cisco Firepower。
User-Agent(UA)
每個瀏覽器/工具連線時的「自我介紹字串」,例如「我是 Windows 的 Chrome 126」。
LLM(大型語言模型)
像 ChatGPT 那種 AI 大腦。AI 攻擊工具靠它決定「下一步怎麼打」。
Payload
攻擊字串本身,例如一段想讓伺服器執行的惡意指令。
404
伺服器回「找不到這個網址」。掃描器亂猜網址時會製造大量 404。
Session / 連線
一次完整的來回連線。同一個人可同時開很多條。
egress(對外連線)
從某台機器「往外」連出去的流量。AI 攻擊工具要對外連 LLM 大腦,就是一種 egress。
MITM 側錄 proxy
中間人代理:把流量導過一個會記錄內容的中繼站,用來側錄瀏覽器做了什麼。Artex 內建這個來擷取自己的攻擊流量。

1. 背景:AI agent 攻擊是什麼

「AI agent(AI 代理)」是一種會自己做決定的攻擊程式。它不是照死腳本跑,而是:看一下目標現況 → 問 AI 大腦(LLM)下一步 → 執行 → 再看 → 再問,不斷循環,直到達成目標。Artex 就是這類工具(本案已知三份 log 是它打的)。

💡 白話解釋 把它想成「一個不會累、會看說明書、還能同時分身的自動滲透員」。它和傳統掃描器最大的差別是會思考、會隨現況調整;和真人的差別是它的思考有固定節奏、而且可以複製很多個一起做。這兩個差別,正好在網路 log 上留下可偵測的痕跡。

★ 資料來源的真相(必讀,先搞懂這個再看證據)

本案 SIEM 沒有收完整的 Web 存取紀錄(web access log)。各設備的收錄範圍差很多,直接決定了「哪些證據可信、哪些有偏差」:

設備收錄範圍能給什麼偏差
FW(PAN-OS)全收每條連線都記IP、埠、session、時間、流量(連線層)無偏,但沒有網址/UA/內容
WAF(SecureSphere)只在觸發規則時收網址、UA、HTTP 方法、payload(內容層)有偏、稀疏:看不到「沒被擋」的請求
IPS(Firepower)只在命中簽章時收攻擊簽章類別有偏:只有命中的那幾筆
💡 白話解釋想像你只有「保全『按下警報』的那幾個瞬間的錄影」,而不是整天的監視器。WAF/IPS 給的就是「警報瞬間」——只有觸發規則的請求才被記下來,沒觸發的(例如正常枚舉、讀 JS、打一般 API)完全看不到。只有 FW 像「門口的進出登記簿」,每個人進出都記,但只記「誰在幾點進出、待多久」,不記「他在裡面做了什麼」。

這對我們的證據有三個直接後果:

  1. 真實的「請求節奏」要用 FW 算,不能只用 WAF。WAF 事件之間的間隔是「兩次『觸發警報』之間」,不是「兩次請求之間」。還好我們用完整的 FW 連線資料重算過,10/14、10/15 的節奏依然成立(見 §1.5)。
  2. 「覆蓋率 / 404 比例」這類指標做不到。因為看不到沒被擋的請求,無法計算「它總共打了多少、猜錯多少」。先前任何「404 很低」的說法在此收回。
  3. 10/16 這天特別弱:它的 FW 幾乎只有連線結束(end)事件、沒有連線建立(start)事件,內容幾乎全靠 WAF(有偏)。所以 10/16 的判斷信心低於 10/14、10/15。

1.5 我憑什麼說是 AI,不是腳本或真人?(核心論證)

「一般攻擊者」只有兩種:真人,或腳本/掃描器。要主張是 AI agent,就必須同時排除這兩者。這一節把推理攤開,並誠實標明哪些證據站在完整資料上、哪些只是推論。

第一步:先承認——很多訊號其實分不出「AI vs 腳本」

下面這些不能當決定性證據,因為寫得好的腳本/掃描器也做得到:

訊號腳本做得到嗎
輪換多個 User-Agent✅(UA 清單輪播)
路徑變異繞過✅ sqlmap tamper、ffuf
多框架 payload 齊射✅ nuclei 就是把模板打一輪
高並發 / 重打狀態端點 / 「很規律」✅ 掃描器更兇、更規律(固定 sleep)
💡 白話解釋只看這些,我頂多說「是自動化」,不能說是 AI。要分出 AI,得靠下面「兩個軸的交集」。

第二步:兩個軸的交集 = AI agent

軸一　機器的「速度/規模」→ 排除真人　站在完整 FW 資料上

用全收的 FW 連線資料(非 WAF 取樣)重算:

  • 10.14:連線建立 649 次,中位間隔 3 秒,爆發群 83 個(最大一群 190 條連線)。
  • 10.15:連線建立 662 次,中位間隔 3 秒,爆發群 69 個。
  • 同時維持多條並行連線。
為什麼排除真人:真人的手不可能用 3 秒中位間隔持續建立數百條連線、又同時維持多線。這一軸是完整資料、最硬。(10.16 FW 缺 start 事件,此軸較弱。)

軸二　人類式的「隨機應變」→ 排除腳本

(a) 停頓是「可變思考時間」,不是固定 sleep。 完整 FW 資料的停頓:

10.14(FW)10.15(FW)
不同的停頓秒數54 種50 種
變異係數 CV6.646.06
為什麼排除腳本:固定 sleep 的腳本停頓會是 1~2 種值、CV≈0;零延遲掃描器則沒有這段停頓。這裡有 50+ 種值、CV 高達 6,且分佈是「一叢短停頓 + 長尾」——符合「想得多就停得久」的可變推理時間。

(b) 它打的是「從剛讀到的內容才知道」的 app 專屬端點。★ 最難偽造,但也最受資料限制

WAF 記到的觸發請求裡,有 users-online-counter、/common/sendlogindata 這種任何通用字典都沒有的 app 專屬路徑,且前面有抓 JS 的動作。腳本靠「預先寫死的字典/模板」,不會因為「剛讀到什麼」而改打什麼。

⚠️ 誠實標註(資料限制):這一點我無法 100% 證明。因為 WAF 只記觸發規則的請求(見「資料來源的真相」),我看不到完整請求流,無法證明「這個請求確實是被上一個回應的內容觸發的」,也無法算 404/字典比例。這些 app 專屬路徑「確實出現過」是事實,但「它是讀懂後才打的」目前是強推論,不是實證。要變實證,需要 response 關聯或 referer 鏈。

(c) 遇阻即時換對應手法(被擋 → 換出對應的繞過寫法,非照清單盲跑)。同樣只看得到觸發的那幾筆,屬佐證。

第三步:四方對照(加入「進階流水線」才誠實)

⚠️ 重要修正我原本寫「只有 AI 兩軸同時有」。這過強,已修正。除了真人和簡易腳本,還有第四種對手:進階自動化流水線(crawler → endpoint extractor → scanner → OAST + 非同步 worker + jitter/backoff)。它兩軸都有——速度/規模有、連「讀了再打、遇阻變形」的適應性也部分有。所以兩軸交集真正排除的是真人與簡易腳本,排不掉進階流水線。
判準真人簡易腳本進階流水線AI agent本案
3 秒中位建連線、多線並行(軸一)❌✅✅✅FW 證實
停頓=批次+等待(非固定 sleep)—❌✅(backoff/頁面等待)✅FW 證實
打 app 專屬端點(先讀後打)❌❌✅(JS extractor)✅推論
遇阻換變形✅慢❌✅(tamper)✅佐證
結論缺軸一缺右三兩者在 SIEM 上幾乎無法分
💡 所以能下的結論是這批活動是「非真人、高度自動化、具目標適應能力的 agent-like 活動」,且與 Artex 架構相容(本次已知來源就是 Artex)。但「它一定是 AI 而非進階流水線」——SIEM 單獨證不到。

第四步:那「AI vs 進階流水線」到底靠什麼分?

靠 SIEM 看不到的東西,只有這些能真正把線劃清(見 §8):

  1. Response 驅動因果:後續請求用到「只有前一個回應才出現」的隨機 endpoint / 自訂參數名 / 一次性 token。這能把「適應式」和「固定模板」分開。
    ⚠️ 但注意:這只證明「會看回應調整」,不等於 LLM——有回饋迴圈的進階 scanner 也可能部分通過。
  2. Artex 內部 telemetry 對時(最強、且能指名 Artex):讓 Artex 帶 X-ARTEX-Run/Task/Tool-ID,把內部事件↔網路事件一對一對上。這才能把「停頓=某次 LLM 推理」從架構相容升級成因果。
誠實的綜合判定 已確認:非真人、高度自動化、多階段、目標適應(FW 完整證實速度/規模與可變停頓)。
已知來源=Artex(本次測試標註),可作行為基準;行為與 Artex 架構相容。
未達成:對「未知來源」強歸因為 AI/Artex——需上面 1、2 的因果證據。
信心:中高(限 agent-like 層級;10.14/15 較高、10.16 較弱)。

2. 分析方法(可重現)

  1. 讀 Artex 原始碼,搞清楚它「怎麼發請求、怎麼計時」——這是痕跡的來源。
  2. 把三份 log 用 Python 解析,抽出:時間、來源 IP、目標、網址、HTTP 方法、User-Agent、各種判斷欄位。
  3. 把「有網址的 WAF 事件」依時間排序,計算節奏(爆發、停頓);統計 UA 種類;分類網址(API/敏感路徑/JS 檔);找繞過變形與攻擊字串。
  4. 把每個觀察對回 Artex 的程式碼機制,再轉成偵測規則。
💡 白話解釋我們沒有「猜」,是先看工具的程式碼知道它會怎麼動,再回頭在 log 裡找對應的腳印,兩邊對得上才下結論。附錄有重現用的欄位與邏輯。

5. 七個 pattern 逐條拆解

讀法提醒以下每個 pattern 都是「與 Artex 架構相容」的行為證據(L2),不是「已證明由某段 Artex 程式碼直接造成」(L3)。而且除了真人/簡易腳本,進階自動化流水線也能產生多數 pattern(見 §1.5)。請把它們當「agent-like 可疑度」的加分項,不是「AI 鐵證」。
P1「想一下、打一批」的節奏★ 最強訊號
💡 白話解釋AI 每做一個動作前都要「問一次大腦」,問一次要等好幾秒。所以它的攻擊變成「打一下 → 等大腦(停頓) → 再打一下」。我們看到打一小批(2~5 個、幾乎同一秒)→ 停約 17~20 秒 → 再一批,重複上百次。真人節奏雜亂、掃描器一路狂衝不停,只有 AI 會這樣規律地停下來「想」。

對應 Artex 程式碼

// agent/deferred.go — 一則 LLM 回應可含「多個」工具呼叫 → 批次執行(造成同秒微爆發)
for _, b := range m.ToolUses() { ... }

// agent/provider.go — 連 LLM 端點(預設 Anthropic 格式、streaming);等它回應 = 停頓
default:
    c.Format = llm.FormatAnthropic         // provider appends "/v1/messages"
    if c.Model == "" { c.Model = "claude-opus-4-8" }  // 推理延遲 ≈ 停頓 17~20s
為什麼對得上:「一次回一批動作」=同秒微爆發;「等大腦回答」=17~20 秒停頓。兩個程式行為剛好拼出 log 看到的節拍。
P2單一來源冒出多種、還假造的 User-Agent
💡 白話解釋User-Agent 是瀏覽器的「自我介紹」。正常人開一個瀏覽器,從頭到尾都講同一句。但這次同一個 IP 講了 7~11 種不同介紹,還有物理上不存在的版本(等於拿假證件)。這只有「程式在拼裝、偽裝」才會發生。

💡 白話解釋網站的前端程式碼(JavaScript)像一張藏寶圖,寫了所有後台入口。傳統掃描器不看圖,拿「常見網址字典」一個個硬猜,大多猜錯留下一堆 404。這個 AI 會先把藏寶圖抓下來讀懂,直接走到真的入口,所以它打的幾乎都是真實存在的功能。

P4系統化換寫法繞過(路徑變異)
💡 白話解釋WAF 會擋某些網址。它被擋後把同一個網址「換個寫法」再試:多個斜線 //、加 /./、中間插 ;x=1。對電腦指到同一處,卻可能騙過防火牆。它一種一種系統化地試,是自動化在找破綻。

P5一次灑多種框架的攻擊(跨框架 payload)
💡 白話解釋不同網站用不同技術蓋的(Java 的 Struts/Log4j、微軟 .NET…),各有各的攻擊法。真人通常先判斷你用哪種再出手;這個 AI 在短時間內把各種攻擊法全丟一輪,哪個中算賺到——這是機器才有的「廣度優先」。

log 證據(欄位:requestMethod 內的字串 + Firepower 簽章)

  • payload:${sys:java.version}(Log4Shell)、%{(#_=1)}/--%{7*7}(Struts2 OGNL)、PROPFIND(WebDAV)、gEt(大小寫變造)
  • Firepower INTRUSION 簽章共現:400:1:58744(61 次)、58742、58723、58737…
對應 Artex:多 worker 並發 + planner 分派(server/conversations.go、agent/planner.go),對同標的廣度優先嘗試多類弱點。
P6每做幾步就回頭看狀態(re-poll)
💡 白話解釋它每做幾個動作就重打同一個「狀態查詢」網址幾百次——像一個人每走一步都先確認「我現在在哪、登入了沒」。這是程式迴圈的特性,人不會這樣。
log 證據:users-online-counter 在 10.14 被打 368 次、10.15 被打 487 次,遠高於其他端點且散佈全程。對應 agent/worker.go 迴圈的「觀察步」+ 瀏覽器輪詢。
P7同時開多條會思考的攻擊線(並發)
💡 白話解釋它最多可同時開 5 條攻擊線一起打,每條各自有自己的「問大腦」節奏。人只有一條線;傳統掃描器開很多條但每條一模一樣、不會各自思考。所以我們看到同一個 IP 同時有好幾串「各自有節奏」的請求。
log 證據:同一來源同標的同時數條並行 session(PAN-OS session 欄位)。對應 server/conversations.go:587 的 maxParallel: 5。

7. ArcSight 相關性規則 R0–R6

💡 白話解釋這是可實作的「邏輯草稿」,不是能直接匯入的檔案。做法:R1~R6 各自抓一種行為、各給分數寫進一張清單(Active List);R0 把分數加總,夠高就告警。關鍵是「合分」:一條規則會誤報,多條一起中才準。

R0 — 加權合分與分級判定

💡 修訂R0 不直接判「AI Agent Detected」,改分級:自動化偵察(3–4)→疑似適應式自動化(≥5)→高信心 response 驅動 agent-like(≥5 且有因果)→已知 Artex(有內部 telemetry 對時)。分數=agent-like 可疑度,非 AI 機率。

同一(來源, 標的)在 1 小時內累計分數:R1=3、R3=2、R6=2、R2=1、R4=1、R5=1。總分 ≥5 → High;3–4 → Medium。動作:產生關聯事件、升 priority、寫入觀察名單。

R1 — Burst-and-Pause 自動化活動 權重 3

💡原名「Turn 節奏」已改。這條抓「批次+等待交替」的自動化型態,不等於 LLM 推理(停頓也可能來自頁面等待、OAST 輪詢、backoff)。主資料源用完整 FW 連線,非 WAF。

抓什麼:「打一批→停 10–25 秒→再打」重複。資料:WAF,Group By 來源+標的,10 分鐘窗。門檻:符合「同秒≥2 筆的微爆發 → 10–25s 停頓」交替 ≥6 次,且同秒占比 ≥40%。實作:aggregation 計同秒簇 + Data Monitor 看 inter-arrival 是否雙峰(次秒峰+10–25s 峰)。誤報調校:排除健康檢查、監控探針、CDN。

💡 白話這條就是抓「機器在想」的呼吸節奏,最難偽造,所以給最高分。

R2 — 多工具 / UA 輪替 權重 1

💡證明多工具/偽裝,不證明 AI。「畸形版本」須比對事件當日實際 Chrome 版本,勿憑直覺。

抓什麼:同一來源短時間內用太多種 UA,或用了假造 UA。門檻:1 小時內 distinct UA ≥5,或命中畸形正則。

Safari/1[23][0-9]\b            # Safari 版號抄 Chrome(不可能)
Chrome/1[5-9][0-9]\.          # 不存在的過高 Chrome 主版本
Chrome/[0-9.]+/[0-9]          # 雙 build number,如 134.0.6998.35/36
^Mozilla/5\.0\s*(\(.*\))?\s*$ # 截斷、無 AppleWebKit 的殘缺 UA
^(curl|cURL|i305-probe|norma/) # 工具 UA 與瀏覽器 UA 同源共現

誤報調校:內網 NAT 出口(很多人共用一個 IP)會抬高 UA 數 → 對內網放寬、對外部單源從嚴。

R3 — 前端探索 → app 專屬探測 權重 2

💡證明「探索後接探測」的整合工作流,不等於 LLM 理解;不得用 404 比例(收不到未觸發請求)。

抓什麼:先抓一堆 JS、又精準打一堆真實 API,而且 404 比例低(不是字典暴力)。門檻:.js ≥10 且 analysisEndpointCategory ∈ {Application API, File Access} 的 distinct 路徑 ≥15,之後重複命中這些路徑;可加「404 比例 < 30%」。

R4 — 系統化 Endpoint 變形 權重 1

💡要當 agent 證據,需加「前一請求被擋後才出現對應新變形、順序隨結果改變」的序列條件;否則只是繞過字典。

門檻:1 小時內 analysisIsPathMutation=True ≥10,或網址命中變形正則 ≥10。

(/\.\./)|(//)|(/\./)|(;jsessionid=)|(;x=\d)

R5 — 多技術類型弱點掃描 權重 1

💡最像「多模板批次」,非 AI 專屬;維持低權重,不得與 R1 相加判 High。

門檻:同來源 1 小時內觸發 ≥2 個不同框架類別的攻擊訊號(Struts/OGNL、Log4j/JNDI、WebDAV、SQLi、反序列化)。升級:若同時 R1 命中 → R0 直接判 High。

💡高頻狀態端點也可能是 SPA 輪詢/heartbeat,非必為 Worker 觀察;並發證明平行,不證明「每條線在思考」。
